# Code Planner

코드를 쓰기 전에 계획을 사용자와 함께 정한다. 같은 플러그인의 훅이 승인된 계획 없이 코드
파일을 쓰는 것을 막으므로, 이 절차를 건너뛰면 코드를 쓸 수 없다.

## 기준 문서

계획을 세울 때마다 새로 읽는다. 사본을 두지 않는다.

| 기준 | 위치 |
|---|---|
| 읽히는 코드 | 이 스킬 폴더 기준 `../write-readable-code/SKILL.md` |
| 14개 루브릭 | 이 스킬 폴더 기준 `../../rubric.md` |
| 최소 구현(ponytail) | Glob `~/.claude/plugins/cache/*/ponytail/*/skills/ponytail/SKILL.md`, 없으면 `~/.claude/skills/ponytail/SKILL.md`. 둘 다 없으면 계획안 4번에 "ponytail 기준 미적용(설치 안 됨)"이라고 쓴다 |
| 교훈 | `~/.claude/code-planner/lessons.md`. 없으면 빈 파일로 만든다 |

## 절차

1. **재료 확인.** 스펙 문서, 구현 계획, 이전 대화에서 만들 것을 찾는다. 없거나 모자라면 사용자에게
   묻는다: 무엇을 만드는지, 왜 필요한지, 입력과 결과, 끝났다고 볼 기준. 재료에 답이 있는 질문은
   다시 묻지 않는다.
2. **기존 코드 읽기.** 관련 진입점, 도메인 규칙, 같은 일을 하는 기존 코드, 기존 테스트 스타일을
   읽는다. 교훈 파일도 읽는다.
3. **설계 질문.** 애매한 지점만 한 번에 하나씩 묻는다. 기본값이 분명한 것은 묻지 않고 계획안에
   적는다.
4. **계획안 제시.** 아래 7개 항목으로 보여준다.
   1. 만들거나 고칠 파일 목록
   2. 메서드·함수 이름과 각각의 책임, 진입 메서드의 흐름 순서
   3. 기존 코드와의 연관: 재사용할 것, 충돌 가능성, 중복 위험. 새 프로젝트면 "해당 없음"
   4. ponytail 관점에서 빼도 되는 것
   5. write-readable-code 관점 점검: 이름이 동작을 예측하게 하는가, 용어가 일관적인가
   6. 14개 루브릭 예측: 항목마다 `위험 / 괜찮음 / 해당 없음`과 이유 한 줄
   7. 테스트 계획: 규칙마다 테스트 이름(정책이 읽히게), 구현 전에 쓸 것과 구현 후에 쓸 것 구분
5. **승인.** 사용자가 승인한다고 말하기 전에는 계획 파일을 만들지 않는다. 고칠 부분을 말하면
   반영해 다시 보여준다. 승인되면 아래 형식으로 저장한다.
6. **테스트 먼저 → 구현.** `tests_first` 짝의 테스트를 먼저 쓰고 실행해 실패 출력을 사용자에게
   보여준다. 처음 실패는 컴파일 오류여도 된다. 그다음 시그니처만 만들어 기능이 없어서 실패하는
   것을 한 번 더 보여주고, 통과하도록 구현한다.
7. **마무리 확인.** 계획의 테스트 파일이 모두 생겼는지, 테스트가 통과하는지 확인하고 결과를
   보고한다.

계획이 과하게 크면(파일이 많거나 추상화가 늘어나면) ponytail 기준으로 줄여 다시 보여준다.

## 테스트를 먼저 쓰는 범위

| 테스트 먼저 (`tests_first` 짝) | 구현 후 |
|---|---|
| 계산, 상태 전이, 중복·권한 검증, 예외 규칙. DB·HTTP·외부 API 없이 검증할 수 있는 도메인·서비스 로직 | Repository 쿼리, Controller 응답, 외부 API 연동, 배치, 트랜잭션 |

- 도메인 단위 테스트는 mock을 쓰지 않는다. 서비스 테스트는 외부 의존성만 mock한다.
- 실패한 테스트를 지워서 통과시키지 않는다.

## 계획 파일

위치: 프로젝트 루트의 `docs/code-plans/YYYY-MM-DD-<작업명>.md`. 경로는 프로젝트 루트 기준,
`/` 구분, 따옴표 없이 쓴다. `files`에는 테스트 파일도 넣는다. glob(`src/**/*.py`)을 쓸 수 있다.

```markdown
---
status: approved
approved_at: 2026-09-29T14:05
files:
  - src/main/java/com/example/Settlement.java
  - src/test/java/com/example/SettlementTest.java
tests_first:
  - impl: src/main/java/com/example/Settlement.java
    test: src/test/java/com/example/SettlementTest.java
---

(계획안 1~7)
```

- `approved_at`은 실제 승인 시각을 쓴다.
- frontmatter에는 `status`, `approved_at`, `files`, `tests_first`만 쓴다. 다른 키가 있으면 훅이
  승인되지 않은 계획으로 본다.
- 사용자가 "계획 없이 그냥 해"라고 하면 `status: skipped-by-user`로 만들고 본문에 이유를 적는다.
- 팀 저장소처럼 계획 파일을 커밋하면 안 되는 곳이면 사용자에게 확인하고 `docs/code-plans/`를
  `.gitignore`에 넣는다.
- 훅은 git 저장소 밖의 파일, `docs/` 아래 파일, 루트에 `.code-planner-off`가 있는 프로젝트,
  계획 없는 기존 파일의 세션 누적 5줄 이하 수정을 통과시킨다.

## 교훈

사용자가 계획을 거절하거나 고쳤을 때, 또는 나중에 품질 측정에서 찾은 위반이 계획에서
"괜찮음"으로 예측했던 부분일 때, 교훈 한 줄을 제안한다. 사용자가 승인한 것만
`~/.claude/code-planner/lessons.md`에 `YYYY-MM-DD | 상황 | 교훈 | 출처` 형식으로 추가한다.
스스로 기준을 바꾸지 않는다.

## 하지 않는 것

- 사용자 승인 없이 `status: approved`를 쓰지 않는다.
- 훅에 막혔을 때 `.code-planner-off`를 만들거나 수정을 5줄씩 나눠 돌아가지 않는다. 계획을 세운다.
- 주석으로 무엇을 하는지 설명하지 않는다. 이름으로 드러나지 않으면 이름을 고친다. 주석은 이유만.
